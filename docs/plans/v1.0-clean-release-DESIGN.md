## 3. gstack vetting — adapted, because the startup frame does not fit

`yc-idea-vet` assumes a startup with customers and revenue. ZakApp is an **open-source
credibility project**. The skill's *Internal Tool Special Rules* are the correct frame, and
its own test is: *"Will the founder use it within 7 days of deployment?"*

That answer is **yes**, and unusually strongly — Salim runs his own zakat, hawl and nisab
through this app, and did so this session (500 payments / 1,000 assets seeded). User #1 is
real, named, and present. That is a stronger demand signal than most startups can produce.

Where the startup questions do bite:

- **Q2 Status quo** — the real competitor is a spreadsheet plus a calculator plus guesswork.
  Strong (people tolerate real pain here).
- **Q4 Narrowest wedge** — one sentence: *"It computes your zakat correctly, tells you when
  it is due, and shows its reasoning."* That is already the product. Do not widen it.
- **Q6 Future-fit** — strengthens with AI (methodology transparency gets more valuable as
  more tools become opaque). No provider dependency. Good.
- **Ralph critique (pass 2), and it is the important one:** the plan inherited from Phase 6
  is **UI-heavy and trust-light**. It optimizes how the app looks while the stated goal is
  whether it can be *trusted*. A user does not call an app stable because the sidebar is
  pretty; they call it stable when it does not lose their data, does not crash on a tap (it
  did, this session), and does not miscalculate. **Section 4 re-weights accordingly.**

## 4. The work — eight items, in dependency order

Ordered so that each is independently reviewable, and so correctness is funded before polish.
Item numbers are the recommended SEQUENCE, not a claim that A is more valuable than B.

### A. Correctness & Durability ("it can be trusted") — FIRST

The class of bug found three times in one component this session: **RxDB's `required` list is
far smaller than the TypeScript type**, so fields the types promise are legally absent at
runtime and every display site is a crash risk.

- Sweep every display site for optional-field misuse. Prove each fix by reverting it.
- Establish a **zakat-math regression suite** with hand-checked expected values, independent
  of the implementation. This is the single highest-value test in the repo: if the math is
  wrong, nothing else matters.
- Durability: offline behaviour, sync failure recovery, and what happens to a user's data when
  sync breaks mid-write. "Reliable" means this, not a spinner.

### B. Sharia Compliance & Methodology Audit

The differentiator, and Salim's explicit ask: *"following Islamic principles in a much
comprehensive way and not deviated the Quran and Sunnah."*

- Audit every calculation rule against its cited source. Each rule in the app should state
  **which** madhhab/standard it follows and **why**.
- Gold/silver nisab basis, the 401k net-withdrawable rule, liability treatment, hawl start
  determination, lunar-vs-solar year handling.
- Every fiqh claim in the UI **verified against a real source or removed**. No invented
  attributions — the standing rule. Where the app is uncertain, it says so.
- Output: a methodology document users can audit. This is the moat.

### C. App Shell — sidebar + tabbar

The single biggest reason the app "doesn't look like the mockup". Replace the dropdown navbar
with the approved persistent left sidebar (desktop), grouped main / LEARN / YOU, active-row
tint; 5-item bottom tabbar on mobile. Slim top bar (logo, theme, notifications, avatar).
Touches every page's frame — one commit, judged in isolation.

### D. Component Vocabulary

Add the missing primitives mirroring the mockup's `ui.css` (198 lines — a small, bounded
surface): `IconChip`, `ListRow`, `Chip`/`StatusPill`, `Segmented`, `PageHead`, `Banner`,
`Snackbar`, `Fab`, `EmptyState`. Purely additive; nothing consumes them yet, so risk is near
zero. Building these before C and E means those land using real primitives instead of
hand-rolled markup that gets rewritten later.

### E. Dashboard Rebuild + Moon-Arc

To the mockup's hierarchy: greeting → **hero zakat figure** (display-size, Outfit, tabular) →
hawl card with moon-arc → quick actions → wealth summary → asset rows. Spec already written in
`BUILD-BRIEF.md` (semicircle, progress stroke, waxing-gibbous glyph, three labels). Must handle
0% and 100% cleanly and be labelled — the arc is decorative, the numbers carry the meaning.

### F. Remaining Pages

Assets, calculator, payments, nisab/hawl, settings, analytics, knowledge hub — each its own
commit.

### G. Code Cleanup ("Clean Code")

Salim's earlier ask, not in the inherited plan. Delete what is dead, collapse what is
duplicated, and minimise honestly. Grounded in evidence, not vibes: five npm projects with no
workspaces; a root manifest carrying Prisma for a server that is not the deployed path; dead
Tailwind classes already swept (11,388 verified). Measure before and after, and report the
delta rather than a feeling.

### H. Release Hardening ("stable release")

- **Email/domain trust:** ✅ DMARC live on `zakapp.org`; DKIM confirmed (`resend._domainkey`,
  `send.zakapp.org`). Remaining: decide whether `rstlabs.io` should stay `p=none`.
- **GitHub native secret scanning:** ✅ enabled, with push protection.
  NOTE: the v1.0 smoke password is still exposed in four develop-only commits on the public
  repo — accepted, deferred 2026-09-24. Rotation is the real fix, and it is still open.
- Dependency pass for the 21 major bumps, **one at a time with tests green after each** — a
  dedicated pass, never alongside a design window.
- Release criteria written down and mechanically checked, so "stable" is a gate and not an
  opinion.

## 5. How gstack vetting is wired into every item

Nothing above is "done" because it looks done. Each item carries a gate:

| Gate | Question | Evidence required |
|---|---|---|
| **G1 Bites** | Does the check fail when the thing breaks? | Revert the fix, observe the failure, restore |
| **G2 Measured** | Before/after numbers, not adjectives | Contrast counts, test counts, byte/diff sizes |
| **G3 Real-world** | Exercised in a browser on seeded data | Screenshot or extracted DOM, not a source read |
| **G4 Traced** | Every caller checked, not just the reported path | `grep` output over all call sites |
| **G5 Honest** | Uncertainty named, not smoothed | "I read this, I did not test it" is allowed |

**Ralph Loop application:** each item gets a first pass, then a self-critique pass that asks
*"what would make me lower this score?"* and searches for that evidence, then a pass that
either fixes it or accepts the lower score explicitly. No inflation without proof.

## 6. Superpowers workflow

- **Brainstorm** (done — this document; architectural path, full spec + approval).
- **Plan** → `writing-plans`: bite-sized 2–5 minute tasks, exact paths, per-item verification.
- **Execute** → fresh subagent per task where the task is context-heavy; in-session batches
  where continuity matters. Never parallel implementation subagents on shared files.
- **Review** → one whole-branch review with a single fix dispatch.
- **Finish** → verify tests, then present merge/PR/keep. Merge target is `develop`.
