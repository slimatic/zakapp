**Opened:** 2026-09-25. **Line:** `develop`. **Approved by:** Salim (in chat, 2026-09-25).
**Scope:** Items A and B from `v1.0-clean-release-DESIGN.md` first; item C delegated

---

## 1. The hard constraint that shapes the team

`delegate_task` has **no per-spawn model argument**. Delegation routes through a single
top-level `delegation.*` block in `~/.hermes/config.yaml`
(`tools/delegate_tool.py::_resolve_delegation_credentials()` reads it).

Measured consequence: **all children of one `delegate_task` call share one model.** Kimi and
deepseek children cannot run simultaneously without racing on that config.

Config is re-read per spawn (proven this session: the delegation swap to
`deepseek-v4.1-flash` took effect with no gateway restart). So the fix is **sequenced
batches**, not simultaneous ones: flip the block, run the batch, flip it back.

This is the single biggest token-efficiency lever we have, so the plan is built around it.

## 2. Token discipline

Rules, in force for every child:

1. **Recon children are read-only and return worklists, not diffs.** Grep-heavy exploration
   produces enormous output; it stays in the child's context and only the distilled
   worklist comes back. This is the main reason to delegate at all.
2. **Never two children on the same file.** Parallel writes to one path corrupt work.
   Parallel reads are always fine.
3. **Children write tests first, code second.** A failing test is a precise spec and costs
   almost nothing; prose specs are expensive and ambiguous.
4. **No child re-derives what a checker already enforces.** The repo has 8 `check-*.py`
   scripts and a 16-test zakat regression suite. Children run them; they do not rewrite them.
5. **The parent does judgment work; children do mechanical work.** Verification of any
   fiqh claim is mine, never a child's.

## 3. Item A — Correctness & Durability

### A1. RxDB `required` vs TypeScript type drift (the documented crash class)

Measured starting point — five schemas, `required` is materially shorter than the type
in each:

| Schema | `required` |
|---|---|
| `asset.schema.ts` | `id, name, type, value, acquisitionDate, isActive` |
| `liability.schema.ts` | `id, name, type, deductibleAmount, isActive, dueDate` |
| `nisabYearRecord.schema.ts` | `id, userId, status, hawlStartDate` |
| `paymentRecord.schema.ts` | `id, userId, amount, paymentDate` |
| `userSettings.schema.ts` | `id` |

The type promises fields the DB may legally omit at runtime → every display site reading
them unguarded is a crash. Asset already shipped this bug three times.

**Deliverable:** a worklist of (schema field, type field, display site, guard needed), then
guarded access at each site. **Gate G1:** revert one guard, watch it fail, restore.

### A2. Zakat-math regression suite — extend, do not rebuild

`client/src/core/calculations/__tests__/zakatMath.regression.test.ts` **exists and is green**
(16 tests): nisab selection per school, the `>=` obligation boundary, the 2.5% rate,
negative-net-worth floor, debt-deduction scope per school, jewellery exemption, decimal
precision.

**Deliverable:** extend to the uncovered surface the design doc names:
- 401k / retirement net-withdrawable rule (three `RetirementMethodology` modes exist in
  `src/types/asset.types.ts`)
- hawl start determination
- lunar vs solar year handling (`core/calculations/hijri.ts`)
- liability treatment beyond the current cases

Values must be **hand-checked independently**, not snapshotted from the implementation —
a snapshot test proves the code is unchanged, not that it is correct.

### A3. Durability

Offline behaviour, sync-failure recovery, and what happens to a user's data when a write
fails mid-sync. Report findings before fixing; scope depends on what is actually found.

## 4. Item B — Sharia Compliance & Methodology Audit

**The deen boundary governs this item, and it is the highest-risk work in the plan.**

- Children **extract claims and locate code**. They do **not** attribute sources.
- **No new fiqh claims are introduced.** Ever. A wrong citation corrupts the thing this
  app exists to serve.
- Every claim already in the code is **verified against its cited source or marked
  unverified**. Where the app is uncertain, it must say so rather than round to confidence.
- Any question of religious obligation routes to a named human scholar — **Ustadh Ali
  Hazratji**, **Sheikh Abdellah El-Khalti**, or **Suhba Seminary** faculty under **Shaykh
  Mokhtar Maghraoui**. The app does not issue rulings.

**Deliverable:** a methodology document users can audit — each rule stating which
madhhab/standard it follows and why, with its source verified. This is the moat, and it is
worth more than the entire visual redesign.

**Gate (non-negotiable):** every attribution in the output traces to a retrieved source or
is explicitly labelled `UNVERIFIED`. No exceptions, no plausible reconstructions.

## 6. Team roster and why each choice

| Role | Model | Rationale |
|---|---|---|
| **Architect / verifier** | parent (me) | Judgment, fiqh verification, gates. Never delegated. |
| **Recon & worklist** | `deepseek-v4.1-flash` ×2 parallel | Mechanical, huge output, read-only. Cheap and fast; output stays in the child. |
| **A implementation** | `deepseek-v4.1-flash` ×2 parallel | Test-first fixes on disjoint files. |
| **B claim extraction** | `deepseek-v4.1-flash` ×1 | Mechanical extraction only — no attribution authority. |
| **C implementation** | `kimi-k2.6` (ollama-cloud) | Stronger multi-file UI reasoning; the one item worth the heavier model. |
| **Peer review** | the *other* model | deepseek reviews kimi's C diff; kimi reviews A's diff. Keeps them honest. |

**Why not bigger models everywhere:** cost. Ollama bills per token and cache hit rate is
near zero in our logs, so a heavy mix runs into the hundreds per month while a flash-first
mix fits the existing plan. Judgment concentrates in the parent; the expensive model is
spent only where file-count and coherence actually demand it.

## 7. Sequence

1. **Phase 1 — recon (parallel, deepseek):** A1 schema/type audit + B claim extraction.
   Both read-only. Returns two worklists.
2. **Phase 2 — A fixes (parallel, deepseek):** disjoint files, test-first.
   Meanwhile the parent drafts the B methodology doc from the claim worklist.
3. **Phase 3 — kimi batch:** flip `delegation.model` → `kimi-k2.6`, run C, flip back.
4. **Phase 4 — peer review:** cross-model diff review, then gates.
5. **Gates:** full suites, 8 `check-*.py`, a11y, `tsc`, `eslint`. Revert-and-fail proof
   (G1) on at least one guard per item.

## 8. Honest risks

- **Fabricated fiqh is the top risk.** Mitigated structurally: children cannot attribute.
- **Kimi on multi-file UI may produce a large diff that is subtly RTL-wrong.** Mitigated by
  the existing a11y gate and the RTL sweep precedent, and by cross-model review.
- **Delegation config is global.** If a kimi batch and a deepseek batch ever overlap, one
  silently uses the wrong model. The plan is sequenced specifically to prevent this; the
  risk is real if a batch is ever launched concurrently.
- **A3 scope is unknown** until investigated. Not estimated here rather than guessed.
